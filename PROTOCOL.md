# Research protocol

This document says what the loop does, what each safeguard is for, and what it
cannot do. The code in `autosci/` enforces the mechanical parts. The rest is a
discipline for whoever runs the loop, human or AI.

## 1. What "reducing hallucination" means here

An AI assistant can write a plausible number, citation or conclusion that nothing
supports. This protocol does not make that impossible. It makes it detectable,
by following one rule:

> Nothing is reported as a finding unless it can be traced to code, a seed, and
> an independent check, or to a source that was recorded as read.

Generation and verification are kept apart. The step that produces a result is
never the step that grades it.

## 2. Stages

1. **Frame.** Turn the idea into a question that has an answer a computation or a
   verified source can give. If it has none, the loop is the wrong tool; say so.
2. **Preregister.** Write a research card (`cards/<id>.json`): question,
   hypotheses, a falsifier for each, the experiment module, its parameters and
   seeds, and optionally a predicted verdict per hypothesis. Then `lock` it. The
   lock stores the hash of the card and of the experiment source.
3. **Execute.** `run` refuses unless the lock still matches the files. It runs
   every seed and appends a hash-chained entry to `state/ledger.jsonl`.
4. **Verify.** `verify` re-executes from scratch and checks: the ledger chain,
   the lock, that stored results match the ledger, that a fresh run is
   byte-identical, that every independent cross-check passes, and that every
   cited source is recorded as verified.
5. **Report.** The report is generated by code from the recorded run. Hand-written
   interpretation goes in `reports/<id>.notes.md` and appears under a heading
   that says it is not covered by verification. `lint` (also run by `verify`)
   checks the notes against the recorded results; see section 6.
6. **Review.** An independent reviewer (a separate agent with fresh context, shown
   the card, the report and the notes but not the reasoning that produced them)
   reads for unsupported claims, then a human reads the pull request. Until the
   human has read it nothing is "reviewed".

## 3. Hypotheses

Each hypothesis needs a statement and a falsifier: the outcome that would refute
it. A hypothesis without a falsifier is not accepted by `validate`.

A card may record `predicted_verdict` before the run. The report shows predicted
against obtained. Over many cards this gives a record of how often the author's
expectations were right, which is the only honest basis for trusting them.

Verdicts are `supported`, `refuted` or `inconclusive`. `inconclusive` is a
legitimate result and is reported as such, not retried until it changes.

A card may declare `depends_on`: outcomes of earlier cards it builds on, each as
`{card, hypothesis, verdict}`. The card cannot run unless the earlier card is
locked unchanged and its latest run carries that verdict. A card that revises an
earlier design says so with `supersedes`; `govern` limits how deep a chain of
revisions may go.

## 4. Evidence levels

The level is computed by `verify`, never declared by the author.

| level | meaning | what it does not show |
|---|---|---|
| L0 | a check failed or is missing | nothing can be relied on |
| L1 | a fresh re-execution gives byte-identical results | the code computes the right thing |
| L2 | L1, and every independent cross-check passed | that the model matches the real world |
| L3 | L2, and every cited source is recorded as verified | that the source is correct, only that it was read and recorded |

Sources carry an `evidence_kind`. `primary-text` means the evidence file holds the
source's own words. `tool-summary` means it holds a summary produced by a tool or a
delegate, which can omit or distort. Level 3 counts both as recorded; the report
lists the kind next to each cited source so a reader can weigh it.

A cross-check is independent only if its reference value comes by a route that
shares no code with the experiment: a closed form, exact enumeration, or a value
from a verified source. Whether a given cross-check is independent is a judgment
the reviewer must make; the code cannot.

## 5. Rules for the agent

1. Never edit a locked card or experiment. A revised design is a new card id; say
   in the notes which card it replaces and why.
2. Never type a result by hand. Numbers come from `runs/` through the generated
   report.
3. Never cite from memory. A source is cited only after its text was fetched and
   read, and then recorded with `source-add --status verified --evidence-file`.
   A lead that was not read is recorded as `unverified` and cannot be cited.
4. Report negative and inconclusive results with the same prominence as positive
   ones.
5. When a check fails, stop and record the failure. Do not change the check until
   it passes.
6. Prose that interprets a result must say which claims it rests on. Claims
   beyond the recorded results are labelled as conjecture.

## 6. Notes lint

`lint` checks the notes file mechanically. A line may carry a tag:

- `[conjecture]`: the author's opinion; numbers are exempt.
- `[context]`: background from outside this run; it must carry a `[src:ID]`.
- `[src:ID]`: cites a source that is recorded as verified and listed in the card.

Any other line may contain a number only if some recorded number (in the results,
the card, or a count derived from them) rounds to it at the precision written.
Unresolved `DATA_NEEDED` or `CITATION NEEDED` markers are reported, and are errors
under `--strict`. The lint is an aid. It does not catch an unsupported conclusion
drawn from supported numbers, or numbers written out in words.

## 7. Stopping, calibration and the frozen core

- `govern` tells the loop to stop and ask the maintainer after a run of entirely
  inconclusive cards, a run of cards with nothing supported, or a card that sits too
  deep in a chain of revisions. The limits are in `state/governor.json`.
- `calibration` reports how often predicted verdicts matched, excluding calibration
  cards, and says so when there are too few predictions to mean anything.
- `guard` compares the frozen core (the verifier, the calibration card, the tests,
  these rules, the governor limits) with the approved branch. `selftest` attacks a
  copy of the repository and requires every corruption to be caught by the check
  meant to catch it. How the framework may change itself is in `docs/EVOLUTION.md`.

## 8. The calibration card

`cards/auction-calibration.json` is run first and kept as a regression test. It
uses two sealed-bid auctions whose answers are known in closed form, and includes
a negative control, a hypothesis known to be false, which the loop must refute.
If the framework is changed and this card stops verifying, the change is wrong.
Passing it shows the machinery works on known cases; it says nothing about
whether a new question is answered correctly.

## 9. Limits

- Simulation is evidence, not proof. For a claim that is a theorem, a simulation
  at L2 supports it but does not establish it. A formal proof is a different
  route and is not implemented here.
- The ledger detects edits and deletions of past entries. It does not stop someone
  from rewriting the whole file and the repository history; git review covers that.
- Byte-identical reproduction is checked on one Python version at a time. The
  version is recorded in the ledger; a failure on another version is reported as
  a problem to investigate, not ignored.
- The framework checks that a source was recorded as read. It does not check that
  the write-up represents the source fairly. That remains a human check.
- A well-designed card can still ask the wrong question.
- `selftest` measures only the corruptions it lists. Its blind spots are printed with
  every score and repeated in `docs/EVOLUTION.md`. A full score is not a safety result.
- A source summary produced by a tool can be wrong. The registry stores its hash, which
  proves which text was read, not that the text is right.
